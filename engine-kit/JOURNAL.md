# Journal - method insights

**Scope**: method

The kit's product journal (technique T51): one line per method insight, learned in a case
or in the kit's own work, kept here until it graduates into the kit. Method only - never a
case's domain, names or paths; `kit_lint.py` checks this file against every case's
deny-list like any other.

## Rules

1. **Method only.** A line says how to work, never what a case's business does. Evidence is
   described by the kind of case: *case zero* (the modernization of a legacy business
   application, with a second legacy system of the same company - an integration service),
   *case two* (a multi-developer product team), *kit* (the kit's own work), *outside kit*
   (an external kit analysed by a case).
2. **One insight per line, append-only.** A new line goes at the bottom of the table, dated
   the day the insight arose. A line is never reworded, reordered or deleted; the only edit
   allowed is its last column, when the insight lands or is dropped.
3. **The one-session deadline.** A method lesson learned in a case becomes a line here in the
   same working session - the next one at the latest. A line still `open` when the next
   minor version is cut is either distilled into that version or marked
   `dropped: <reason>`.
4. **How a line graduates.** When the insight generalises and has evidence, it becomes a new
   row of the technique register ([`docs/techniques.csv`](docs/techniques.csv), labelled by
   [`docs/MATURITY.md`](docs/MATURITY.md): one case makes it `operating` or `candidate`), or
   it strengthens an existing row, skill, agent or tool. The version's CHANGELOG entry names
   it, and the line's last column gets the row id or the path and the kit version that
   carries it (tag or CHANGELOG version) - only once the text is in that file; until then the
   column says `open`. **Pulling a case's outbox line means writing its line here**, in the
   release that carries the fix: a CHANGELOG entry that describes the fix is not a pull, and
   the case cannot mark its own line landed without this one. A landing corrected after the
   fact (another piece, another version) is also a CHANGELOG line, so the case sees it. An idea never run in a case
   is marked `design` and waits for its first case.
5. **Where the lines come from - the self-improving prompt.** A long effort run from a
   master prompt or a front prompt
   ([`front-protocol`](skills/front-protocol/SKILL.md)) keeps two companion sections:
   **STATUS**, the checkpoint (phase, what is done, the exact next action - precise enough
   for a cold session to resume), and **LEARNINGS**, the log (date, phase, observation,
   proposed action). Every session ends by evaluating the run (what worked, what caused
   rework, where the kit was missing or ambiguous, which instruction got in the way),
   logging it, applying low-risk fixes to the prompt itself with a changelog line, and
   proposing structural ones to the owner. A learning marked "kit candidate" becomes a line
   here within the session; the kit is never edited from a copy inside a case
   ([EK#1](DECISIONS.md)).

*Landed in* says where the insight lives now: a technique row (`T14` - registered, whether
or not the row is in the kit yet), a kit path, `open`, `design` (an idea with no case
evidence, no implementation), or `dropped: <reason>`.
